**1. 필요한 공개 자료는 존재하지만, 자료의 종류를 구별해야 한다.** 색과 발광 원리, 효과 명칭과 영상, 공연 편집 방식은 비교적 잘 공개되어 있다. 이번 조사에서는 ‘화약 성분을 입력하면 완성된 불꽃의 외형과 시간을 정확히 산출하는 재사용 가능한 공개 데이터셋’은 확인하지 못했다. 이는 그런 데이터셋이 전혀 없다는 뜻은 아니다.

**2. 하늘의 색점은 ‘별(star)’이라는 발광체로 이해하면 된다.** 축제의 대표적인 공중 불꽃에는 작은 고체 발광체인 별이 사용된다. 관객이 보는 점과 줄기는 이 발광체의 빛, 이동, 주변에 남는 불티가 합쳐진 결과다. 발광체 자체가 작은 불티 하나와 같은 것은 아니다. [ACS의 별과 발광 설명](https://www.acs.org/education/chemmatters/resources/fireworks-what-do-we-know-about-fireworks/further-exploration-activities.html)

사용자가 궁금해한 ‘실제로 어떤 상태의 재료를 다루는가’에 대한 시뮬레이션 관점의 답은 **역할이 다른 조성물과 성형된 발광 부품이 존재하며, 공연에서는 완성된 효과 단위를 배치한다**는 것이다. 공중 개화, 상승하는 혜성, 지상의 분수는 서로 다른 효과 유형이다. 이 차이를 모든 효과에 하나의 ‘폭발 입자’ 알고리즘만 쓰는 대신, 서로 다른 이벤트 구조로 표현하는 것이 좋다. 별·꼬리·상승 효과를 구분하는 [FWsim의 구성 요소 모델](https://www.fwsim.com/doc/en/effecteditor.html)이 비교할 만하다.

화학 구성의 역할과 가상 엔진의 대응은 다음처럼 구분할 수 있다. 오른쪽은 이 프로젝트에 대한 설계 제안이다.

| 실제 구성에서의 역할 | 엔진에서의 대응 |
|---|---|
| 에너지와 산소 공급 | 미리 정한 움직임·발광 프로필 |
| 발색 | 시간에 따른 색·밝기 곡선 |
| 발광체의 형태 유지 | 별이라는 시각 객체 |
| 상승과 개화의 시간 관계 | 효과 내부 이벤트 마커 |
| 발광체와 작은 불티의 차이 | 부모 별과 꼬리 입자의 별도 수명 |

화학의 역할 구분은 [Nebraska 대학의 설명](https://chem.unl.edu/news/rebecca-lai-and-chemistry-fireworks/)을 참고했다. 표는 화학 반응에서 실제 궤적을 계산하는 변환표가 아니다.

색과 관련해 먼저 확보할 설명 데이터는 아래 정도면 충분하다.

| 참고하는 계열 | 대표적인 색 인상 | 가상 재질 이름의 예 |
|---|---|---|
| 스트론튬 | 진홍·적색 | 진홍색 발광 |
| 구리 | 청색·청록 계열 | 청색 발광 |
| 바륨 | 녹색 계열 | 녹색 발광 |
| 나트륨 | 노란색 | 노란색 발광 |
| 칼슘 | 주황색 | 주황색 발광 |

이 관계는 교육용 요약이다. 기체 상태 발광종의 스펙트럼과 고온 입자의 열복사는 구별해야 한다. 금빛·은빛이라는 명칭이 금·은 원소를 뜻하지는 않는다. [ACS 교육자료](https://www.acs.org/education/chemmatters/resources/fireworks-what-do-we-know-about-fireworks/further-exploration-activities.html), [C&EN의 발광 원리 취재](https://cen.acs.org/articles/95/i27/s-fireworks-produces-those-colorful.html)

엔진에서는 원소명과 RGB를 일대일로 고정하지 않는 편이 좋다. 실제 보이는 색은 발광종, 밝기, 주변 빛, 연기, 카메라와 표시 장치에 영향을 받는다. 초기에는 색 계열을 선택하고 별의 색·꼬리의 색·밝기를 따로 편집하게 만들 수 있다. ‘화약을 세팅하는 재미’는 이러한 발광 재질, 별의 배치, 꼬리 성격, 시간별 변화의 조합으로 구현하는 안을 제안한다.

**3. 효과는 형태와 시간 변화로 분해하면 재사용하기 쉽다.** 아래 12개를 첫 분류 후보로 정리했다. 용어와 외형의 근거는 [Finale의 효과 용어집](https://finale3d.com/documentation/vdl-effect-glossary/)과 [FWsim의 효과 구성 설명](https://www.fwsim.com/doc/en/effecteditor.html)이다. 계산 방법은 제안이다.

| 효과 | 구별되는 외형 | 계산 방법의 제안 |
|---|---|---|
| Peony · 모란형 | 둥근 점 무리 | 구면 방향 분포 |
| Chrysanthemum · 국화형 | 둥근 줄기 무리 | 별과 독립적인 불티 |
| Willow · 버드나무형 | 길게 처지는 잔광 | 긴 수명과 감속·낙하 |
| Brocade | 금빛의 촘촘한 반짝임 | 재사용 가능한 꼬리 스타일 |
| Palm · 야자형 | 굵고 성긴 가지 | 소수의 방사 방향 |
| Ring · 고리형 | 원형 윤곽 | 평면 분포와 방향 |
| Pistil · 꽃심 | 외곽 안의 중심 | 겹친 시각 이벤트 |
| Comet · 혜성형 | 상승하는 줄기 | 상승 발광체 |
| Mine · 지상 부채형 | 아래에서 퍼지는 빛 | 지상 원뿔 분포 |
| Fountain · 분수형 | 지속되는 불티 | 연속 입자 방출 |
| Crossette | 진행 중 십자 분기 | 자식 이벤트 |
| Multi-break · 다단 개화 | 이어지는 여러 개화 | 시간 관계를 가진 이벤트 트리 |

이 목록은 같은 층위의 분류가 아니다. Brocade는 꼬리 성격, Pistil은 중심 구조, Multi-break는 시간 구조에 가깝다. 내부에서는 **형태 + 재질/꼬리 + 시간 변화 + 복합 이벤트**로 나누고, 사용자가 보는 프리셋 이름으로 묶는 편이 조합에 유리하다.

깜빡임이나 색 전환도 별도 수정 속성으로 두는 것이 좋다. 예를 들어 ‘청색 국화형 + 금빛 꼬리 + 끝부분 색 전환’을 하나의 거대한 전용 알고리즘 없이 구성할 수 있다. 첫 시각 검증은 Peony, Chrysanthemum, Willow로 하고, 방향 문제를 확인할 Ring과 상승 효과인 Comet을 이어서 추가하는 안이 적절하다.

**4. 논문은 서로 다른 질문에 답한다.** 아래 자료들은 모두 같은 의미의 ‘물리적으로 정확한 불꽃 시뮬레이션’을 검증한 것이 아니다. 확인한 범위를 넘어서 결과나 성능을 추정하지 않았다.

우선순위는 입자 생명주기 → 별과 불티의 구분 → 시간별 발광 → 복합 형태 제어 순으로 잡는 것이 좋다. 새로운 화학 조성을 연구한 논문의 제조 조건은 이 웹앱에 필요하지 않다. 연구에서 관찰한 작은 불티의 동작을 대형 공중 불꽃 전체의 법칙으로 확대하는 것도 피해야 한다.

**5. 인터뷰에서 드러나는 중요한 작업은 ‘공연을 구성하는 일’이다.** 한화의 윤두연 디자이너 인터뷰는 콘셉트·선곡·공연 구조가 하나의 업무로 연결됨을 보여준다. 따라서 효과 실험실과 공연 편집 화면을 왕복할 수 있어야 한다. [The Korea Times, 2018](https://www.koreatimes.co.kr/southkorea/society/20180928/interview-fireworks-designer-to-light-up-seoul-skies-oct-6)

NEA의 Phil·Lauren Grucci 인터뷰는 공연 공간과 관객의 시점을 강조한다. 발사대 배치와 관람 카메라를 둘 다 저장해야 한다는 설계적 근거다. 고리나 문양은 카메라에 비스듬하면 다르게 보일 수 있으므로 정면 미리보기만으로 효과를 평가하면 부족하다. [NEA 인터뷰 전사, 2019](https://www.arts.gov/stories/podcast/phil-and-lauren-grucci)

Phil Grucci의 다른 인터뷰에서는 음악의 강약과 정서에 효과의 성격을 맞추는 방식이 드러난다. 일괄 발사, 좌우 흐름, 바깥에서 안쪽으로 이동, 짧은 강조와 긴 여운을 편집할 수 있어야 한다는 제안으로 연결된다. [Profoundly Pointless, 2021](https://profoundlypointless.com/episodes/2021/6/29/fireworks-show-designer-phil-grucci)

이 인터뷰들은 각각의 창작 경험이다. 이를 전 제작사의 표준 공정이나 현재의 내부 소프트웨어 사양으로 해석하지는 않았다.

**6. 시간축의 기준은 처음부터 명확해야 한다.** 전문 도구는 발사 신호부터 음악에 맞출 시각적 순간까지의 간격을 prefire로 구분한다. 공중 불꽃에서는 개화, 다른 효과에서는 상승의 시작 등이 관심 시점이 될 수 있다. [Finale prefire 설명](https://finale3d.com/documentation/prefire/)

사용자의 후속 설명에 따라 트리거를 저장하는 다음 모델로 정리했다.

- 효과 자산은 ‘시작으로부터 상승·개화·최대 펼침·마지막 잔광’ 같은 상대 마커를 갖는다.
- 공연의 큐는 ‘언제, 어느 발사대에서, 어떤 효과를 시작할지’를 저장한다. 실행 시간의 단일 기준은 cue.atTick이다.
- 개화 시각에 맞추는 편집 기능은 상대 마커를 이용해 트리거 시점을 계산할 수 있다. 이는 편집 보조 기능이며, 계산된 입자의 궤적이나 프레임 결과를 저장하는 뜻은 아니다.
- 타임라인에는 발사 위치 표시, 주목할 시각 마커, 효과가 남아 있는 구간을 구별해 그린다.
- 시작 시점이 공연의 0보다 앞서면 준비 재생 구간을 두거나 해당 큐를 수정하게 한다. 조용히 잘라내지 않는다.

예시 JSON은 초당 120개의 정수 tick을 쓰는 가상 공연이다. 이는 설명을 위한 선택이며 확정 정밀도나 권장 성능 수치가 아니다. 첫 큐의 트리거는 900 tick, 즉 7.5초다. 예시 효과 정의에 있는 상대 개화 마커 300 tick을 더하면 개화 예정 시각은 1,200 tick, 즉 10초가 된다. 실제 시각 상태는 그 시간까지 효과 런타임이 계산한다.

~~~json
{
  "id": "cue-a",
  "launcherId": "left-outer",
  "effectId": "red-peony-v1",
  "atTick": 900,
  "seed": "cue-a"
}
~~~

시간차 시퀀스는 ‘왼쪽→오른쪽’, ‘중앙→바깥’, ‘양끝→중앙’, ‘동시’, ‘반복’을 작은 패턴으로 제공할 수 있다. 같은 효과를 쓰더라도 위치·순서·간격만 바꿔 공연의 인상을 바꿀 수 있다. [FWsim의 stepper와 공간 편집](https://www.fwsim.com/doc/en/show_editor.html)이 직접적인 비교 사례다.

그룹으로 만든 큐를 개별 편집할 때는 연결된 패턴을 유지할지 독립 큐로 풀지를 사용자가 선택하도록 제안한다. 생성된 큐의 ID는 편집 도중 유지해야 하며, 순서를 바꿀 때마다 새 ID를 만드는 방식은 피하는 편이 좋다.

**7. Rust는 적합한 후보지만, 렌더링 비용은 별도로 관리해야 한다.** wgpu는 WebAssembly에서 WebGPU와 WebGL2 실행 경로를 제공한다. 다만 WebGL2에는 compute shader가 없다. WebGPU용 GPU 계산을 그대로 켜서 자동으로 호환시키는 구조로 생각하면 안 된다. [wgpu 웹 실행 문서](https://wgpu.rs/doc/wgpu/documentation/platforms/web/index.html), [wgpu 기능 제약](https://wgpu.rs/doc/wgpu/struct.DownlevelFlags.html#associatedconstant.COMPUTE_SHADERS)

권하는 초기 역할 분담은 다음과 같다.

~~~mermaid
flowchart LR
    A["웹 편집 UI<br/>효과·발사대·타임라인"] --> B["공연 JSON<br/>효과 자산·큐·카메라"]
    B --> C["Rust / Wasm<br/>이벤트·시간·재생 상태"]
    C --> D["wgpu 렌더러<br/>별·불티·연기·빛"]
    D --> E["3D 관람 화면"]
    F["카메라 트랙"] --> D
    G["음악 시간"] --> C
~~~

이 구성은 제안이지, 두 엔진을 구현해 비교한 결과가 아니다.

| 부분 | 첫 구현 제안 | 이후 확장 |
|---|---|---|
| 편집 UI | TypeScript로 선택·드래그·속성 폼 | 큰 타임라인과 고급 효과 편집 |
| Rust 코어 | 이벤트 순서, seed, 가상 운동, 재생·탐색 | 병목이 확인된 계산의 최적화 |
| GPU | 묶어서 그리는 별·불티, 후처리 | 많은 장식 입자의 GPU 계산 |
| 연기 | 적은 수의 부드러운 연기 입자 | 필요한 경우 저해상도 유체 모델 |
| 소리 | 별도 오디오 시간축과 효과 이벤트 | 관객 위치에 따른 공간음 |
| 저장 | JSON 원본과 재생성 가능한 별도 캐시 | 큰 프로젝트 저장 최적화 |

입자 운동은 가상 장면 단위의 중력, 감속, 바람으로 시작할 수 있다. 별이 퍼진 뒤 느려지고 처지며 소멸하는 느낌을 맞추고, 가상 상승 경로는 효과의 시각 마커와 일관되게 만든다. 화약의 양에서 압력과 실제 발사 속도를 계산하는 모델은 이 제안에 포함되지 않는다.

별의 밝기와 색은 나이에 따른 곡선으로, 불티는 별에서 분리되어 자기 수명을 갖는 입자로 표현하는 안이 좋다. 분기 효과는 새 이벤트로 만들고, 연기는 별보다 오래 남는 별도 시스템으로 다룬다. 전체를 한 종류의 입자로 취급하면 효과마다 다른 잔광과 분기 표현을 만들기 어려워진다.

Rust를 쓴다는 이유만으로 속도 향상을 보장할 수는 없다. 입자별로 JS 객체를 만들거나 경계를 반복해서 넘기지 말고, 변경 명령과 계산 결과를 묶어 전달하는 설계를 검토해야 한다. [wasm-bindgen의 벤치마크 설명](https://wasm-bindgen.github.io/wasm-bindgen/benchmarks/)도 실제 앱 성능과 미시 벤치마크를 구분한다.

브라우저는 이름만 보고 지원 여부를 판단하지 않고 실제 GPU adapter, 기능, 한도를 확인해야 한다. WebGPU 미지원 시 ‘지원 안내’를 할지 ‘낮은 품질의 WebGL2 모드’를 제공할지는 구현 전에 결정할 사항이다. 후자를 고르면 CPU에서 계산하는 경로나 다른 셰이더 경로가 필요하다. [MDN WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)

**8. 카메라와 잔광을 제대로 다루는 것이 사용자의 구상에 특히 중요하다.** 아래는 구현 시 확인해야 할 그래픽스 설계 제안이다.

- 꼬리를 이전 화면의 잔상만으로 만들면 카메라를 옮길 때 번짐이 따라올 수 있다. 불티와 주요 꼬리는 3D 공간에 남겨야 한다.
- 카메라가 뒤로 이동하는 것과 시야각을 바꾸는 것은 구도가 다르다. 위치·바라보는 점·시야각을 따로 저장한다.
- 가까이서 설정할 때와 멀리서 관람할 때 같은 불꽃을 유지한다. 카메라 변경이 입자 난수나 궤적을 바꾸면 안 된다.
- 빛나는 입자는 발광 합성이, 연기는 가림과 투과가 중요하다. 연기까지 전부 밝게 더하는 방식은 피한다.
- 밝은 점의 중심, 바깥 빛 번짐, 주변 연기 조명을 구분해 조절한다. 과한 빛 번짐이 모든 색을 흰색으로 만들지 확인한다.
- 링·하트 같은 평면형 효과는 방향을 저장한다. 관람 카메라를 따라 자동으로 정면을 유지시키는 연출을 넣는다면 별도의 창작 옵션으로 표시한다.

긴 노출의 사진은 멋진 형상 참고가 되지만, 그 선 길이를 실시간 불티의 수명으로 그대로 취급할 수 없다. 먼저 실시간 영상의 움직임과 밝기 변화를 기준으로 맞추고, 사진처럼 오래 누적하는 표현은 별도 관람 효과로 두는 편이 적절하다.

줌아웃하면 화면의 입자 크기는 줄지만 보이는 불꽃의 수는 늘 수 있다. 따라서 줌아웃을 자동으로 ‘더 가벼운 장면’으로 가정하지 않는다. 불꽃이 겹치는 피날레, 화면을 넓게 덮는 꼬리, 연기, 빛 번짐을 함께 켠 상태에서 실제 GPU 시간을 확인해야 한다.

**9. JSON은 재생 입력이고, 되감기는 그 입력을 목표 시점까지 다시 평가하는 동작이다.** 앞선 ‘JSON 저장만으로는 해결되지 않는다’는 표현은 결과 상태도 파일에 저장해야 한다는 뜻으로 읽힐 여지가 있었다. 필요한 효과 자산·환경·seed·모델 버전이 함께 재현된다면, JSON 입력을 다시 실행하는 것으로 상태를 복원할 수 있다. 스냅샷은 탐색 속도를 위한 선택적 캐시다.

| 데이터 | 저장할 내용 | 성격 |
|---|---|---|
| 공연 설정 | 포맷 버전, 시간 단위, 길이, seed, 모델 버전 | 원본 |
| 공간 | 발사대 ID, 위치, 방향, 환경 설정 | 원본 |
| 효과 자산 | 형태·발광·꼬리·이벤트 마커와 버전 | 원본 |
| 큐 | 고유 ID, 효과 참조, 발사대 참조, 기준 시각 | 원본 |
| 카메라·음악 | 키프레임, 음악 자산 참조, 시간 관계 | 원본 |
| 입자·연기·이벤트 대기열 | 특정 시점의 계산 상태 | 재생성 가능한 캐시 |
| 선택 상태·패널 크기 | 편집기 사용 상태 | 별도 UI 상태 |

예시에는 효과의 편집 입력을 effectDefinitions로 넣었다. 이는 입자 상태의 스냅샷이 아니다. 실제 엔진에서는 공유 효과가 업데이트되더라도 예전 공연이 갑자기 달라지지 않도록 필요한 자산과 버전을 함께 고정하는 편이 좋다. 예시의 포맷 버전·모델 버전은 모두 연구용 표시이며 아직 호환 계약이 아니다.

부분 편집을 안정적으로 만들려면 다음 원칙이 필요하다.

- 같은 cue ID와 seed는 같은 이벤트의 난수 기준을 유지한다. 다른 큐의 삽입으로 모든 불꽃의 난수가 밀리지 않게 한다.
- 난수는 쇼·큐·효과 노드·입자 ID를 바탕으로 나누고, 난수 알고리즘과 이벤트 처리 순서를 모델 버전에 포함한다.
- 하나의 효과를 여러 큐가 공유할 때 ‘선택한 큐만 변경’은 복제본을 만들어 연결하고, ‘전체 변경’은 영향받는 큐를 표시하는 방식을 제안한다.
- 변경 캐시의 무효화 시작점은 눈에 보이는 개화 시각보다 앞선 실제 가상 시작 시각을 포함한다. 옛 시작과 새 시작 중 더 이른 시점부터 다시 계산한다.
- 카메라만 바뀌면 물리 상태 캐시는 유지하고 화면을 다시 그린다. 바람 등 환경이 바뀌면 해당 시점부터 영향을 받는 상태를 다시 계산한다.
- Undo/Redo와 복사·붙여넣기에서도 자산 참조·ID·seed가 어떻게 유지되는지 규칙을 정한다.

초기 탐색 구현은 상태를 초기화하고 목표 시각까지 재생하는 방식으로 충분하다. 서로 독립적인 효과는 각자의 트리거 시점부터 평가할 수도 있다. 나중에 탐색이 느리면 가장 가까운 유효 스냅샷부터 이어서 계산하는 경로를 추가한다. 이때 캐시에는 별뿐 아니라 불티, 연기, 대기 중인 자식 이벤트 등 복구에 필요한 상태가 포함되어야 한다. 부모가 사라진 뒤 자식이 나타나는 효과도 있으므로 최근 몇 초의 큐만 실행해서는 언제나 같은 장면을 복원할 수 없다.

계산 간격을 고정하고 표시 프레임 사이를 보간하면 재생 속도와 렌더링 주사율을 분리할 수 있다. 같은 버전의 이벤트 재현성과 서로 다른 GPU에서 픽셀까지 같은 결과는 다른 목표다. 후자까지 필요하다면 부동소수점·GPU 연산 차이까지 별도로 설계해야 한다. 초기에는 같은 엔진의 큐·분기·수명 재현을 우선 목표로 제안한다.

음악이 있을 때는 음악 재생의 시간축을 기준으로 공연을 맞추고, 일시정지·재개·구간 이동에서 재생 기준점을 갱신해야 한다. 오디오 컨텍스트 시간은 시스템 시각과 별개이며 중단 중에는 진행하지 않는다. 정밀도 제한도 고려해야 한다. [MDN 오디오 시간 문서](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/currentTime)

**10. 현실감을 높이기 위한 다음 자료 수집은 영상의 ‘관찰값’이어야 한다.** 아직 이번 조사에서 영상을 프레임별로 측정하거나 실제 불꽃 데이터를 추출하지는 않았다. 다음 단계는 다음 항목을 가진 짧은 참고 클립 기록을 만드는 것이다.

| 관찰 항목 | 기록할 값 또는 조건 | 피해야 할 추정 |
|---|---|---|
| 출처 | URL, 제공자, 구간, 이용 조건 | 공개 영상의 자유로운 재배포 가정 |
| 시간 변화 | 상승·개화·최대 펼침·소멸의 상대 시각 | 편집·슬로모션을 정상 속도로 취급 |
| 형태 | 정규화된 반경, 원형성, 가지 수의 인상 | 단안 영상에서 정확한 실제 크기 추정 |
| 색·밝기 | 상대 변화와 색 계열 | 노출 불명 영상에서 절대 광도 추정 |
| 꼬리 | 남는 길이와 소멸 변화 | 사진의 긴 노출을 실제 수명으로 취급 |
| 바람·연기 | 흐르는 방향과 시각적 가림 | 카메라 이동을 바람으로 취급 |
| 시점 | 카메라 고정 여부, 대략적인 관람 방향 | 2D 한 장면에서 유일한 3D 구조 복원 |

초기 효과를 프리셋별로 한 장면씩 맞춘 다음 여러 발사대의 겹친 연출에서 평가하는 편이 좋다. 같은 효과도 카메라와 연기에 따라 인상이 달라지기 때문이다. 자동으로 원소 조성과 영상을 연결하려 하기보다, 시각 프로필의 출처와 보정 수준을 기록하는 것이 당장 구현에 유용하다.

**11. 첫 구현은 사용자가 말한 한 번의 작업 흐름을 끝까지 이어 주는 것이 좋다.** 고급 노드 편집기보다 효과 선택과 몇 가지 속성을 바꾸는 폼으로 시작하고, 나중에 내부 이벤트 트리를 노출하는 안을 제안한다.

| 단계 | 만들 결과 | 완료를 판단할 증거 |
|---|---|---|
| 시각 검증 | 대표 효과 3개, 가까운/먼 카메라 | 형태·꼬리·처짐이 서로 구별되는 녹화 |
| 배치와 연출 | 여러 발사대, 동시·시간차 큐 | 위치·순서·간격 변경이 기대대로 반영 |
| 저장과 탐색 | 저장·불러오기·중간 재생·되감기 | 같은 공연의 이벤트와 잔광이 복원 |
| 편집 완성 | 선택한 큐 수정, Undo/Redo, 구간 반복 | 다른 큐와 공유 효과가 의도대로 유지 |
| 품질 확장 | 연기·소리·복합 효과·성능 조절 | 대상 기기의 대표 장면과 피날레 측정 |

이번 JSON 예시가 표현하는 범위는 다음과 같다.

- 총 45초의 가상 공연.
- 발사대 5개, 효과 설정 3개, 큐 10개.
- 10초부터 0.5초 간격의 왼쪽→오른쪽 개화.
- 30초부터 양쪽이 대칭을 이루며 안쪽으로 이어지는 피날레.
- 시작 지점의 가까운 카메라에서 전체 공연을 보는 위치로 이동.
- 공연 파일에 저장된 효과 설정과 고정된 큐별 seed.

이는 JSON으로 의도를 표현한 예시이며 실제 시뮬레이션을 실행한 결과는 아니다. 효과의 최대 펼침 위치와 카메라 구도는 엔진을 만든 뒤 화면에서 확인해야 한다.

첫 성능 검증에서는 지원할 기기·브라우저·화면 해상도를 먼저 고른다. 단일 효과와 겹치는 여러 효과, 긴 꼬리와 연기가 쌓인 장면에서 프레임 시간·메모리·탐색 지연을 측정한 뒤 입자 상한과 품질 단계를 정한다. 아직 ‘Rust면 수십만 입자도 문제없다’거나 특정 FPS를 보장할 근거는 없다.

구현 전에는 다음 세 가지를 결정하면 범위가 선명해진다.

- 데스크톱 웹을 우선할지, 모바일에서도 편집까지 가능해야 할지.
- 관찰에 맞춘 자연스러움을 기본으로 할지, 정교한 문양을 자유롭게 만드는 연출도 초기부터 넣을지.
- WebGPU 미지원 환경에서 안내만 할지, 별도 호환 모드를 제공할지.

**12. 이번에 확인한 것과 아직 확인하지 않은 것을 구분한다.** 공개 자료의 관련 본문·초록·검색 추출을 읽고 출처별 확인 범위를 기록했다. 효과 분류와 공연 JSON은 연구용 제안으로 작성했다. JSON 3개의 문법, 중복 ID, 출처·효과·발사대·그룹 참조, 시각 조절값 범위, 시각 마커에서 파생한 시작·종료 시간, 카메라 키프레임의 순서·시간 범위, 문서의 로컬 링크를 검사했고 문제를 발견하지 못했다. 예시의 마지막 효과는 41초에 끝나 45초 공연 범위 안에 들어온다.

논문 전문 전체의 정독, 외부 효과 파일 분석, 참고 영상의 프레임 측정, Rust/WebGPU 구현, 실제 브라우저의 성능·시각 검증은 하지 않았다. 작업 폴더에는 기존 앱이나 테스트가 없었으며, 이번 작업은 자료와 데이터 예시 작성 범위다.

조사 결과를 바탕으로 가장 먼저 확인할 장면은 **효과를 조금 바꾸고, 다섯 발사대에 시간차로 배치하고, 카메라를 뒤로 옮겨 관람한 뒤, 큐 하나만 고쳐 같은 공연을 다시 보는 장면**이다. 이 흐름이 안정적으로 재현되는지 확인한 다음 효과의 종류와 편집기의 깊이를 늘리는 방향을 제안한다.
