타임라인 JSON과 효과 런타임의 역할
=================================

정리일: 2026-09-05. 이 문서는 사용자가 명확히 한 실행 모델을 정리한다. 최소 발광체 단위와 가상 배치의 상세 문헌조사는 [별도 의뢰](/Users/carlos-yang/dev/fireworks-simulator/research/external-research/brief.ko.md)로 분리했다. 2026-09-06에 [외부 조사 수신본](/Users/carlos-yang/dev/fireworks-simulator/research/external-research/fireworks-simulation-granularity-research.ko.md)과 [로컬 검토](/Users/carlos-yang/dev/fireworks-simulator/research/external-research/review.ko.md)를 추가했다. 실제 엔진은 아직 구현하지 않았으며, 아래의 구체적인 이름과 자료 구조는 설계 설명이다.

**사용자의 이해가 맞다.** 공연 시간은 JSON에 기록된 트리거들을 지나가고, 각 트리거는 발사대의 정보와 효과 정의를 사용해 실행 중인 효과 인스턴스를 만든다. 불꽃의 움직임·밝기·분기·잔광은 인스턴스가 계산한다. 프레임마다 생긴 결과 좌표를 원본 공연 JSON에 다시 기록할 필요는 없다.

기존 보고서의 ‘JSON 저장만으로는 되감기와 부분 편집이 해결되지 않는다’는 표현은 너무 넓었다. 더 정확한 설명은 **JSON에 필요한 입력을 저장하고, 런타임에 재평가 동작을 구현하면 되감기와 부분 편집을 지원할 수 있다**는 것이다. 재현에 필요한 외부 자산이 있다면 자산과 버전도 함께 확보되어야 한다. 스냅샷을 저장해야만 가능한 구조는 아니다.

**트리거의 흐름과 상태 계산의 흐름은 구별된다.** 아래 그림의 위쪽은 효과를 시작하는 일이고, 아래쪽은 시작된 효과를 시간에 따라 계산하는 일이다.

~~~mermaid
flowchart TD
    A["공연 JSON<br/>이벤트 시점·효과 정의·발사대·seed"] --> B["공연 시간 T / 스케줄러"]
    B -->|"시점을 통과한 이벤트를 한 번 전달"| C["발사대의 생성 시점 위치·방향"]
    C --> D["효과 인스턴스 생성"]
    D --> E["효과 나이 τ = T − 트리거 시각"]
    E --> F["별·불티·연기·자식 이벤트 갱신"]
    F --> G["현재 상태를 렌더링"]
    H["되감기 / 과거 입력 편집"] --> I["영향받는 상태를 버리고 목표 시각까지 재평가"]
    I --> D
~~~

발사대는 이벤트의 출처와 생성 좌표계를 제공한다. 모든 효과에 별도의 전역 시간을 만들어 전달할 필요는 없다. 스케줄러는 공연 시간, 효과는 자신의 나이로 동작하면 된다. 효과 안에서 일어나는 개화나 분기는 해당 효과의 내부 이벤트이며, 공연 타임라인에 모든 작은 불티 트리거를 풀어 적을 필요는 없다.

| 대상 | 책임 | 원본에 저장할 내용 |
|---|---|---|
| 타임라인 | 어떤 효과를 언제 시작할지 결정 | 큐 ID·트리거 시각·참조 |
| 발사대 | 생성 시점의 위치와 방향 제공 | 가상 위치·방향·고유 ID |
| 효과 정의 | 무엇을 어떻게 생성·변화시킬지 설명 | 분포·시각 재질·상대 시간·규칙 |
| 효과 인스턴스 | 이번 한 번의 결과 계산 | 원본에는 저장하지 않는 실행 상태 |
| 렌더러 | 계산된 현재 상태를 화면에 표시 | 필요한 카메라·표현 설정 |
| 재생 캐시 | 계산을 다시 하는 양을 줄임 | 필요할 때 추가하는 파생 데이터 |

**‘항상 계산’은 살아 있는 결과를 계속 갱신한다는 의미다.** 일반적인 순방향 재생에서는 직전 상태에서 다음 시간으로 진행한다. 매 프레임 원점부터 전체 쇼를 재계산하는 것을 전제로 하지 않는다.

개별 효과의 상태를 나이만으로 직접 구할 수 있는 모델도 가능하다. 반대로 불티나 연기처럼 이전 시간의 상태에 의존하는 모델은 시간에 따라 누적 계산한다. 이 선택은 효과 모델에 따라 다르며, 둘 다 같은 타임라인 트리거 구조를 사용할 수 있다.

공연 시간이 여러 이벤트를 한 번에 건너뛰는 프레임에서도 그 사이의 트리거를 빠뜨리지 않아야 한다. 각 효과는 실제 자신의 시작 시점부터 남은 시간만큼 진행시켜야 한다. 시작 시각 0의 이벤트, 동시에 시작되는 이벤트의 순서, 반복 재생 시 인스턴스의 중복 방지는 재생 규칙으로 명확히 두면 된다.

**JSON에는 입력을 저장한다.** [공연 예시](/Users/carlos-yang/dev/fireworks-simulator/research/show.example.json)는 연구용 버전 2로 바꾸어, 각 큐가 직접 트리거 시각을 갖도록 했다. 화면상의 개화 시각을 기준으로 한 최초 예시에서 같은 가상 공연이 나오도록 시작 시각을 변환한 것이다.

~~~json
{
  "id": "cue-a",
  "atTick": 900,
  "launcherId": "left-outer",
  "effectId": "red-peony-v1",
  "seed": "cue-a"
}
~~~

예시의 시간 단위에서는 900 tick이 7.5초다. 이때 효과 인스턴스가 생성된다. 효과 정의의 개화 상대 마커 300 tick에 도달하는 시점은 공연의 10초다. 마커는 효과를 언제 변화시킬지에 관한 입력이며, 그 시점에 각 입자가 어디에 있을지는 계산 결과다.

효과 설정은 effectDefinitions로 이름을 바꿨다. 이전의 effectSnapshots라는 이름은 런타임 스냅샷과 혼동될 수 있었다. 이 설정에 기록된 색·분포·상대 마커는 편집 입력이다. simulationEndTick은 단순 예시의 재생 범위를 설명하기 위한 상대 종료 값이며, 실제 엔진의 복합 효과에서는 자식과 잔광이 모두 끝났는지 런타임이 판정해야 한다. 이후 수명 정의에서 종료 시각을 파생하도록 구체화할 수 있다.

원본에는 이벤트와 함께 가상 배치·환경·seed·모델 버전·효과 자산 또는 자산 버전이 필요하다. 실제 별의 매 순간 좌표, 이미 방출된 불티, GPU 버퍼, 연기 상태는 결과이므로 재생 중 JSON을 갱신할 대상이 아니다.

**되감기는 ‘현재 상태의 시간을 음수로 돌리는 것’보다 ‘과거 입력을 다시 실행하는 것’으로 이해하면 명확하다.** 예를 들어 20초를 보다가 12초로 이동하면 다음 방법으로 충분하다.

1. 현재 실행 결과를 초기화한다.
2. 공연 시작부터 12초까지 필요한 이벤트를 다시 실행한다.
3. 12초까지 각 효과를 진행시켜 해당 시각의 상태를 그린다.

스냅샷 없이도 가능한 기본 동작이다. 다른 효과와 상호작용하지 않는 효과라면 그 효과의 시작점부터 나이만큼 계산할 수도 있다. 반면 공통 환경의 누적 상태에 의존한다면 필요한 이전 구간을 함께 복원해야 한다.

나중에 탐색이 느려질 때 중간 결과를 캐시하는 기능을 추가한다. 캐시는 삭제되어도 원본 입력으로 다시 만들 수 있어야 한다. 불티·연기·대기 중인 자식 이벤트까지 복원해야 한다는 말은 캐시를 도입할 때의 완전성 조건이지, 그 상태를 JSON 파일에 영구 저장하라는 뜻이 아니다.

‘현재 시각에 막 트리거되는 이벤트만 실행’해서 과거 시각을 표시하면, 이미 시작되어 아직 살아 있는 효과를 놓친다. 또한 부모가 사라졌어도 자식 효과나 잔광이 남을 수 있으므로 부모의 종료만으로 전체 인스턴스를 버리지 않는다.

**다시 계산해도 같은 편집 결과를 보려면 난수의 기준을 유지해야 한다.** 개념적으로는 다음 조건이다.

~~~text
현재 상태 = Evaluate(공연 입력, 효과 자산, 환경, seed, 모델 버전, 목표 시각)
~~~

이는 계산을 한 번의 수학식으로 닫힌 형태로 구할 수 있다는 뜻은 아니다. 재현에 영향을 주는 입력을 표시한 것이다. 같은 seed를 쓰더라도 모델·샘플링 알고리즘·이벤트 순서가 바뀌면 결과가 달라질 수 있다.

한 개의 전역 난수열을 모든 효과가 공유하면 앞에 큐 하나를 삽입했을 때 뒤쪽 불꽃까지 달라질 수 있다. 큐와 효과 내부 개체의 고유 ID를 바탕으로 난수의 기준을 나누는 안이 적절하다. 새 변화를 보고 싶을 때만 사용자가 변형 seed를 바꾸게 할 수 있다. 정확한 난수 알고리즘과 기기 간 재현성 수준은 구현 시 정할 사항이다.

**부분 편집은 원본 입력을 바꾼 뒤 영향받는 결과를 재평가하는 일이다.**

| 편집 | 다시 계산할 범위의 원칙 |
|---|---|
| 아직 실행되지 않은 큐의 시간 변경 | 예정된 이벤트 갱신 |
| 이미 시작된 큐의 시간 변경 | 옛 결과 제거, 새 시작부터 현재 시각까지 평가 |
| 한 큐의 효과 설정 변경 | 해당 인스턴스의 정의를 바꾸고 재평가 |
| 여러 큐가 공유하는 효과 정의 변경 | 사용자가 선택한 적용 범위의 인스턴스 재평가 |
| 카메라 이동 | 시뮬레이션 상태를 유지하고 다시 그림 |
| 환경의 과거 값 변경 | 바뀐 입력에 의존하는 상태 재평가 |
| 가상 발사대의 배치 편집 | 영향을 받는 큐의 생성 좌표계를 갱신하고 재평가 |

‘과거의 발사대 위치를 편집한 뒤 재생하는 것’과 ‘공연 도중 발사대가 움직이는 것’도 구분된다. 공중으로 떠난 효과는 기본적으로 생성 시점의 발사대 정보를 사용한다. 이후 발사대를 움직였다고 이미 생성된 공중 효과를 함께 끌고 가면 안 된다. 반면 발사대에 붙어 있어야 하는 연속 효과는 별도의 부착 규칙을 가질 수 있다. 이 차이는 최소 입도와 무관한 좌표계·생명주기 설계다.

초기에는 편집 후 전체를 다시 재생해도 된다. 영향 범위만 재계산하는 기능과 캐시는 같은 동작을 더 빠르게 수행하기 위한 후속 최적화다. 이번 문서에서 특정 캐시 방식이나 Wasm·GPU 구조를 필수 조건으로 확정하지 않는다.

**최소 단위는 별도의 문헌 질문이다.** 타임라인이 트리거만 전달한다는 구조는 효과 내부를 별 하나, 별의 집합, 불티, 연속 분포 중 어느 단위로 계산하든 유지된다.

g은 질량을 나타내는 단위다. 같은 질량이라는 사실만으로 객체 수·위치·시각적 형태가 정의되는 것은 아니다. ‘어떤 관찰 현상을 개별 객체로 취급할지’와 ‘그 객체에 어떤 속성을 줄지’를 나눠 질문해야 한다. 실제 원료의 입도나 충전 단위를 정하는 지침은 이번 조사 범위가 아니다.

외부 조사에는 다음을 맡겼다.

- 원료 입자, 성형된 발광체, 분리된 불티·액적, 집합 모델의 개념적 차이.
- 사용자의 편집 단위, 운동 계산 단위, 렌더링 단위를 분리할 근거.
- 정규화된 가상 좌표의 명시적 목록, 절차적 분포, 부분 override의 비교.
- 같은 개체를 계속 선택·수정할 수 있는 stable ID와 샘플링 규칙.
- 문헌으로 확인할 수 있는 정확도의 수준과 실측이 필요한 부분.

후속 구현의 우선순위는 이 단위를 결정할 근거를 확보하는 것이다. Wasm 최적화, 캐시 간격, GPU 분업, 압축 방식과 수치 상한은 실제로 구현하고 측정하면서 선택한다.
