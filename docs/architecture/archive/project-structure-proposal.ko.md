React CSR과 불꽃 시뮬레이터의 프로젝트 구조안
=============================================

작성일: 2026-09-06. 상태: 구현 전 제안. 현재 저장소에는 조사 문서와 연구용 JSON 예시가 있으며 앱 의존성이나 Rust 크레이트는 아직 생성하지 않았다. React CSR과 Rust 엔진은 사용자가 제시한 방향을 따른다. Three.js·React Three Fiber 사용과 아래 디렉터리 구성은 이번 조사에 따른 권고다.

**권고 구성은 React + TypeScript + Vite, Three.js + 얇은 React Three Fiber 연결, Rust/Wasm 계산 엔진이다.** CSS는 편집 화면과 작은 시각 안내에 사용한다. 이 프로젝트에서 중요한 구분은 UI 프레임워크보다 저장할 편집 문서, 실행 중인 계산 상태, 화면 표현의 책임이다.

**1. React CSR로 시작하는 이유**

주요 동작은 파일을 불러와 편집하고 브라우저 안에서 재생하는 것이다. 이 범위에서는 Vite의 React TypeScript 템플릿으로 CSR 앱을 구성하면 된다. 서버 저장·공유가 추가되더라도 계산 엔진과 뷰포트는 같은 클라이언트 경계를 유지할 수 있다. React 공식 문서는 Vite를 클라이언트 SPA의 시작점 중 하나로 안내한다. 이는 React가 모든 앱에서 프레임워크 없는 구성을 우선 권한다는 뜻은 아니다. [React 공식 안내](https://react.dev/learn/build-a-react-app-from-scratch), [Vite 시작 문서](https://vite.dev/guide/)

**2. 화면과 계산을 나누는 방식**

| 부분 | 담당 | 소유하는 상태 |
|---|---|---|
| React 편집기 | 타임라인, 발사대 목록, 효과 설정, 파일 메뉴 | 편집 문서와 UI 선택·드래그 상태 |
| 재생 제어기 | 재생·정지·탐색·재계산 요청 | 공연 시각과 재생 상태 |
| Rust 코어 | 큐 처리, 효과 생성, 궤적·수명·분기 계산 | 살아 있는 효과와 필요한 이력 |
| Wasm 연결부 | 브라우저와 Rust 사이의 입력·출력 전달 | 모듈 수명과 버퍼 접근 |
| Three.js 뷰포트 | 카메라, 발사대 표시, 발광점·꼬리 그리기 | 장면 객체와 GPU 표현 자원 |
| CSS | 레이아웃, 패널, 선택 표시, 간단한 형태 안내 | 화면 표현 속성 |

~~~mermaid

    UI["React 편집기"] -->|"편집 명령"| DOC["공연 문서"]
    DOC -->|"입력과 문서 버전"| HOST["시뮬레이션 연결부"]
    PLAYER["공연 시간 / 재생 제어"] -->|"진행·탐색"| HOST
    HOST --> WASM["Rust / Wasm"]
    WASM -->|"현재 렌더 데이터"| VIEW["Three.js 뷰포트"]
~~~

스케줄러의 실제 큐 실행은 Rust 코어 한곳에 둔다. TypeScript의 재생 제어기는 어떤 공연 시각을 보고 싶은지 전달한다. 같은 큐를 React 쪽과 Rust 쪽이 각각 실행하는 구조를 만들지 않는다.

원본 JSON은 트리거와 설정이다. 뷰포트가 그린 결과를 원본에 다시 쓰지 않는다. 이전에 정리한 [타임라인·되감기 모델](/Users/carlos-yang/dev/fireworks-simulator/research/timeline-runtime-model.ko.md)이 그대로 적용된다.

**3. 제안하는 디렉터리**

아래는 생성할 구조이며 현재 존재하는 파일 목록이 아니다. 웹 앱 하나와 Rust 코어·브라우저 연결 크레이트 두 개로 시작한다.

~~~text

│   └── web/
│       ├── package.json
│       ├── vite.config.ts
│       └── src/

│           ├── document/            # 편집 명령, undo/redo, 파일 입출력

│           │   ├── launchers/       # 발사대 선택·배치 편집
│           │   └── effects/         # 효과 프로필·개별 수정

│           │   └── interaction/     # 카메라 조작, 선택, 배치 도구

│   │       ├── timeline/            # 결정적인 큐 처리
│   │       ├── effects/             # 발광체·생성기·분기 모델
│   │       └── world/               # 실행 상태와 공통 환경
~~~

`sim-core`는 DOM, React, Three.js 객체를 알지 못하게 한다. 뷰포트에는 코어 결과를 그리는 역할을 주고, 효과의 실제 생성·소멸 판단은 코어에 둔다. 연구용 JSON을 운영 스키마로 바로 선언하지 않고, 첫 수직 구현에서 필요한 입력을 좁혀 버전 규칙을 정한다.

입력 타입의 기준은 한곳에 둔다. Rust의 직렬화 모델을 기준으로 TypeScript 타입을 생성하는 방식을 후보로 삼되, 실제 생성 도구와 직렬화 옵션은 바인딩을 붙일 때 확인한다. 생성한 타입은 런타임 입력 검증을 대신하지 않는다. 같은 필드 목록과 검증 규칙을 양쪽에서 독립적으로 수정하는 상태를 피하는 것이 목적이다.

**4. Three.js와 React Three Fiber의 역할**

Three.js가 3D 장면·카메라·재질·렌더링을 제공한다. React Three Fiber(R3F)는 이를 React에서 구성하고 수명과 프레임 루프를 연결하는 선택 사항이다. 이 앱은 React 편집 도구와 장면의 선택·배치를 함께 다루므로 R3F를 얇게 쓰는 안을 권한다. 직접 Three.js를 붙이는 방법도 가능하다. [Three.js 장면 구성](https://threejs.org/manual/en/creating-a-scene.html), [R3F 애니메이션 안내](https://r3f.docs.pmnd.rs/tutorials/basic-animations)

발광체마다 React 컴포넌트와 상태를 만들 필요는 없다. React는 효과 레이어를 구성하고, 프레임마다 변하는 좌표·색·크기는 참조와 버퍼를 통해 갱신한다. R3F 공식 안내도 연속 업데이트에는 React 상태 갱신보다 객체 참조를 직접 수정하는 방식을 설명한다. 해당 안내는 이번 조사에서 검색 엔진에 색인된 공식 본문으로 확인했다. [R3F 공식 안내](https://r3f.docs.pmnd.rs/tutorials/basic-animations)

기본 발광점은 `Points`와 `BufferGeometry`를 출발점으로 삼을 수 있다. 커스텀 모양이나 크기 제약이 생기면 인스턴스 기반 빌보드 등으로 바꾼다. 꼬리는 별도 표현이 필요하다. `Points`가 모든 효과를 자동으로 해결하거나 항상 더 빠르다는 주장은 하지 않는다. [Three.js Points](https://threejs.org/docs/pages/Points.html), [InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html)

초기 렌더러는 `WebGLRenderer`를 권한다. `WebGPURenderer`에는 WebGL 2 대체 경로가 있지만, 기존 커스텀 셰이더와 후처리를 그대로 교체할 수 있는 것은 아니다. 공식 문서도 재질과 TSL 이식이 필요한 경우를 명시한다. 셰이더를 뷰포트 안에 모아 향후 전환 영향을 좁히고, 실제 전환은 구현·측정 뒤에 판단한다. [WebGPURenderer 공식 안내](https://threejs.org/manual/en/webgpurenderer.html)

**5. Rust/Wasm과 렌더링을 혼동하지 않기**

이번 권고에서 Rust/Wasm은 CPU 측 효과 계산을 맡고 Three.js가 브라우저 그래픽 API를 사용해 그린다. Wasm으로 컴파일했다고 그 계산이 자동으로 GPU 계산이 되는 것은 아니다. 기존 조사에서 살펴본 `wgpu`는 다른 렌더링 경로의 후보였다. Three.js를 주 렌더러로 채택한다면 처음부터 Rust `wgpu` 렌더러도 함께 구축할 이유는 없다. 이는 역할 분리에 관한 설계 판단이다.

처음에는 한 화면에서 한 경로로 계산하고 그린다. Worker, 공유 메모리, GPU 계산, LOD와 캐시 간격은 사용자가 요청한 대로 후속 최적화로 남긴다. 다만 Wasm 모듈 준비·해제와 출력 버퍼의 유효 기간은 최초 연결부터 명확해야 한다.

프레임 출력은 좌표·외관 등 렌더에 필요한 데이터다. 이를 매번 전체 공연 JSON으로 변환해 전달하는 구조는 피한다. 정확한 버퍼 형식은 효과 단위와 첫 구현의 요구를 확인한 뒤 정한다.

**6. 편집·재생·카메라 상태**

| 상태 | 예시 | 저장·변경 원칙 |
|---|---|---|
| 편집 문서 | 큐, 효과 정의, 발사대 배치, seed | 저장과 undo/redo의 대상 |
| UI 상태 | 선택한 큐, 열린 패널, 드래그 중인 값 | 문서와 구분 |
| 재생 상태 | 현재 시각, 재생·정지 여부 | 시간 제어기가 소유 |
| 계산 상태 | 살아 있는 발광체·불티·분기 대기·꼬리 이력 | 입력으로 다시 만들 수 있는 런타임 상태 |
| 관람 카메라 | 자유 회전, 확대, 이동 | 보통 관람 상태로 유지 |
| 연출 카메라 | 사용자가 작성한 카메라 키프레임 | 지원할 때 명시적으로 문서에 기록 |

큐를 옮기면 문서가 바뀌고 영향받는 상태를 재평가한다. 카메라를 돌리면 같은 계산 결과를 다른 시점에서 그린다. 관람 중의 카메라 조작이 자동으로 연출 키프레임을 덮어쓰면 안 된다. 드래그를 마칠 때 어떤 편집 명령을 확정할지도 UI와 문서 경계에서 다룬다.

재생 시간은 앱이 정한 공연 시각을 사용한다. R3F의 장면 시작 이후 경과 시간을 공연 시각으로 직접 사용하면 정지·탐색 규칙과 어긋날 수 있다. 렌더 프레임 루프는 공연 시각을 진행시키거나 읽는 기회로 활용한다.

**7. 구현 순서와 완료 기준**

| 단계 | 구현 범위 | 완료를 확인할 동작 |
|---|---|---|
| 1. 작업 뼈대 | React CSR 화면, 3D 장면, 카메라, Rust/Wasm 로딩 | 개발 화면이 열리고 카메라를 조작하며 코어 연결 성공·실패를 확인 |
| 2. 하나의 효과 | 발사대 하나, 큐 하나, 단순 발광체 모델 | 트리거부터 펼침·소멸까지 재생; 정지·탐색·동일 입력 재생 확인 |
| 3. 여러 발사대와 편집 | 복수 큐, 시간차, 배치 편집, JSON 저장·불러오기 | 한 큐의 시간·위치 수정 후 재생에 반영되고 저장 내용을 다시 읽음 |
| 4. 세밀한 효과 편집 | 분포·프로필, 고정 ID, 개별 수정 | 개체 선택과 수정, 분포 변경 시 수정 보존 규칙 확인 |
| 5. 관측에 맞추기 | 꼬리·분기·잔광·카메라 표현 보강 | 여러 시점과 시간 구간에서 참고 관측과 비교 |

첫 구현은 폴더만 대량 생성하기보다 단계 1–2가 연결되는 작은 범위로 진행한다. 초기에는 느리더라도 정확한 재평가 경로를 확보하고, 부분 재계산과 캐시는 그 동작을 유지하면서 최적화한다. 실행 전에 필요한 아키텍처 선택은 주 렌더러와 R3F 사용 여부이며, 버퍼 계약·스키마를 이번 문서만으로 확정하지 않는다.

**8. CSS 조사와의 연결**

CSS로 입체 배치·확대·회전·대략적인 펼침은 표현할 수 있다. 주 뷰포트의 대체 여부와 구체적인 기법·제약은 [CSS와 Three.js 비교 조사](/Users/carlos-yang/dev/fireworks-simulator/research/css-and-threejs.ko.md)에 따로 정리했다. CSS 예제는 표현 가능성을 확인하는 실험이며 실제 불꽃 엔진이나 운영 스키마를 구현한 것은 아니다.

이번에 준비한 것은 구조 제안, 근거 조사, CSS 표현 확인이다. React 앱 빌드, Rust 컴파일, Wasm 연결, Three.js 성능 비교는 아직 수행하지 않았다.
